# JIT 開発を後回しにするかどうか：判断材料

この文書は、意図書の「Success Metrics」にある判断（JIT 開発を後回しにするかどうか）のための材料をまとめたもの。JIT 開発そのものは行うことが決まっていて、ここで決めるのは時期だけ。閾値はユーザーが決める（要件 FR6.2）。各数値には根拠の種類（検証済み／ドキュメント根拠／推測）を付けた。
- 作成日：2026-10-05
- 対象：blink の fork `aletheia-works/blink@7e1d7439`（インタプリタのみ）、aube v2.6.1（x86-64 static-musl）
- 計測環境：Windows 11、Intel Core i7-8650U（4 コア 8 スレッド）、AC 電源、電源プラン「バランス」、Playwright（headless、ページは前面）

## 1. 結論の要約

- **今の速さ**：最も安定した Chromium で、aube #1645 の 4 コマンドの合計が約 12 秒。CheerpX 1.3.9 と比べると、install は CheerpX の上限と同程度、frozen install は 1.5〜4 倍遅い。WebKit はさらに 1.5 倍ほど遅い（検証済み）。
- **時間の内訳**：コマンドごとの起動は 0.3〜0.5 秒で、install の 9 割以上は解釈実行の時間。ネイティブより約 75〜200 倍遅い（検証済み）。JIT が効くのはこの解釈実行の部分で、効く余地は大きい。
- **私の意見（推測を含む）**：この C 版 blink の fork での JIT 開発は、後回しにすることを勧める。理由は 3 つ。(1) 正しさの未解決事項が残っている。(2) コアは将来 paludarium（Rust 版 blink）に置き換える構想で、JIT への投資はそちらで回収する方が無駄がない。(3) 今の速さでも、#1645 の再現のような確認用途には使える。ただし、ブラウザで日常的に aube を使う体験を目標にするなら、話は別になる（下の「閾値の候補」を参照）。

## 3. JIT で縮む見込み（モデル、推測）

JIT が解釈実行を k 倍速くし、起動の 0.4 秒は変わらないと仮定した、Chromium の install の見込み。k の値は実装次第で、この PoC では測っていない。

| JIT による解釈実行の高速化 k | install（秒） | frozen install（秒） |
| ---------------------------- | ------------- | -------------------- |
| 1（今のまま）                | 5.7           | 5.3                  |
| 2                            | 3.1           | 2.9                  |
| 3                            | 2.2           | 2.0                  |
| 5                            | 1.5           | 1.4                  |
| 10                           | 0.9           | 0.9                  |
- k = 2〜3 で、install と frozen install の両方が CheerpX の範囲に入る。
- k を上げても、起動の固定費（0.3〜0.5 秒）が下限として残る。それ以上縮めるには、blink を常駐させてコマンドをまたいで使い回す仕組みが要る。これは JIT とは独立に取り組める。

## 5. 後回しにする理由と、すぐ始める理由

### 後回しにする理由

- **正しさの未解決事項が残っている**（`docs/results/failures.md`）：WebKit でまれに残る停止（26.9 秒の回）、`madvise(MADV_DONTNEED)` が何もしない実装であること（未検証の潜在的な不具合）、実機の Safari での確認（U-1）。JIT は正しさの問題を増やしやすく、先に土台を固める方が安全（推測）。
- **コアの置き換え構想**：エミュレータのコアは、将来 paludarium（Rust 版 blink）に置き換える予定（commit `8096c7b4` の `aidlc/spaces/default/memory/project.md`、ドキュメント根拠）。C 版 blink の fork に入れた JIT は、置き換えで捨てることになりうる。
- **固定費の問題が別にある**：コマンドごとの起動 0.3〜0.5 秒は JIT では縮まない。体感の改善には、常駐化のような JIT 以外の手も効く。

### すぐ始める理由

- 解釈実行が時間の 9 割以上を占めるので、JIT の効果はほぼそのまま体感に出る（計算）。
- frozen install は、CheerpX の上限より 1.5 倍以上遅い。B を目標にするなら、JIT かそれに代わる高速化が必要。
- WebKit（Safari の代わり）は Chromium より 1.5 倍遅い。Safari の利用者を重視するなら、差は大きい。

## 6. 測っていないこと（判断の前に知っておくべき限界）

- **背面での計測**：CheerpX はページが背面で測っている。formicarium は前面（headless）だけで、背面での速さは未計測（U-2）。
- **ホストの速さの変動**：このマシンは同じ計算の時間が最大 2.4 倍変わる。今回の 10 回はホストが安定していた時間帯の値で、別の時間帯ならもっと遅くなりうる（検証済み、`docs/results/failures.md` の U-2 の調査）。
- **JIT の効果 k**：測っていない。表 3 は仮定に基づくモデル。
- **ほかの機種**：このノート PC 1 台だけで測っている。
- **ほかのツール**：aube だけで測っている。計算の重いツールでは、解釈実行の比率がさらに高くなる見込み（推測）。

## 7. 次に決めること

1. 閾値として A・B・C のどれを採るか（またはほかの基準）。
2. A を採る場合：正しさの未解決事項（WebKit の停止、`madvise`、Safari の実機）を先に片付けるか。
3. B か C を採る場合：JIT をこの fork で作るか、paludarium で作るか。あわせて、起動の常駐化をどうするか。

## 8. 決定（2026-10-05）

ユーザーの判断：**JIT 開発は後回しにする。** 速いに越したことはないが、コアは paludarium（Rust 版 blink）に置き換える構想なので、C 版 blink の fork での JIT より、ほかの作業を優先する。閾値は当面「A. 確認用途で使えれば十分」とし、次は正しさの未解決事項（WebKit でまれに残る停止など）に取り組む。

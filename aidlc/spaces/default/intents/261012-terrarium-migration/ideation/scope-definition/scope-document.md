# terrarium移管の範囲

## 根拠と目的

`../intent-capture/intent-statement.md`の承認済み目的・成功条件、`../feasibility/feasibility-assessment.md`の条件付き実現性、`../feasibility/constraint-register.md`の制約を引き継ぐ。詳細の機能範囲は`docs/terrarium-migration-plan-summary.md`を参照する。以下は計画の定義（ドキュメント根拠）であり、移管・試験・公開の完了報告ではない。

ビルドと検証の重複を減らし、vivariumがformicariumを直接利用できる状態へ移す。デモ閲覧者・再現利用者の利用を維持し、保守者の重複作業を減らす。

## 対象範囲

| ID | 利用者に届ける能力・成果 | 完了条件 | backlog |
|---|---|---|---|
| S0 | 移管を進められるか判断する証拠 | 3ブラウザの取得・工程別時間、baseline1件の実行・2回目再利用を記録。失敗なら代替方式を選び再確認 | B0 |
| S1 | formicariumだけでゲストを検証・操作・導入できる | 公開guest API、共通コマンド、install、進捗/エラー/リセット、Node/3ブラウザ受入、公開版consumer追従、旧入力置換 | B1 |
| S2 | vivariumで再現用の固定ゲストを作成・再利用できる | 完全commitと依存を固定、出所・digestを確認、同入力2回目でビルド省略と同一digestを実証、Release保存 | B2 |
| S3 | vivariumの再現を直接formicariumで利用できる | 端末のready/run/transcriptを維持し、実行前固定値照合、Biomeのbefore/afterが旧verdictと一致、3ブラウザでreproduced | B3 |
| S4 | 下流が移行後の契約を利用できる | Contract v1のformicarium追加とdeprecated terrarium互換、schema/guests/en/ja/テンプレート更新、旧loader/proxy等の依存解消 | B4 |
| S5 | 最新安定版の3ツールデモを継続できる | aube/pitchfork/Biomeの取得・必要なビルド・catalog、公開APIのみ、回帰fixtureと分離、Node/3ブラウザで--version成功 | B5 |
| S6 | 移管先サイトからデモを利用できる | エミュレータ説明と/tools/、install導線、3ツール実行、日次受入と配布、失敗時に前回サイト維持 | B6 |

## 最小成果と全体完了

最初の独立成果はS0の判断材料である。これは製品移管の縮小版ではなく、未検証事項を解消して後続への投資を判断する試行である。旧入力アーカイブは試行時にだけ一時利用でき、全体完了では除去する。

S1は最初の利用可能な移管成果になる。S1だけでは今回の目的は完了しない。全体の最小完了範囲はS0–S7すべてで、デモと再現の両経路が通った後に退役する。各成果は個別に受入・統合でき、途中の段階でも既存terrariumを維持する。

## 対象外

- C forkのJIT、paludariumへのコア置換、動的リンク対応。
- ゲストのネットワーク・シェル・パッケージマネージャ、任意URLからのinstall、パイプ・変数展開・リダイレクトの提供。
- showcaseの別リポジトリ化、3ツールを超えるデモ追加。
- npm/JSRの既存版削除、移行前のterrarium停止。
- 別intentのBun/一般保守CI改善や、既知コア問題の独立修正を今回へ追加すること。

## 優先順位と依存

全S項目をMoSCoWのMustとする。今回の完了目標に含まれない追加機能をShould/Couldとして持ち込まない。順序は最初にリスク解消、その後は依存順とする。

`B0 → B1 → B2 → B3 → B4` と `B1 → B5 → B6`、`B4 + B6 → B7`。B0の固定ビルド試行はB2の最小部分を先取りする。公開API完成前の一時入力使用を許すことで循環依存を避ける。B2では試行を本番用の固定成果物運用へ仕上げる。

## 制約と通過条件

既存品質限界・互換性・ライセンス・公開承認を維持する。固定期限・追加予算は設定せず、新費用は事前相談する。測定と重いビルドは並行しない。Safari実機をWebKit結果で確認済みとしない。

B0が失敗した場合は大規模移管を止め、同originミラー・事前導入・設計見直しの該当案を具体化する。導入時間の数値閾値は要件定義で確定する。作業checkoutと公開版の整合、remoteのcommit存在、CI権限・配布容量は未検証で、各作業前に確認する。

## 利用価値の流れ

計測で移管条件を把握 → 汎用APIで重複処理を集約 → 固定ビルドで再現入力を保証 → vivarium利用者が同じ再現結果を得る → latestデモ利用者が移管先で3ツールを使う → 両経路の移行を確認 → 案内と退役で保守対象を減らす。

## 受入と変更判断

各S項目の証拠を後続の要件・テスト・配送計画へ対応付ける。全体完了はintentの6つの成功目標とS0–S7の達成を照合する。公開・deprecation・archive・infra操作は具体的内容の承認を得る。この範囲の承認で将来の外部操作まで承認されたとは扱わない。範囲・優先度変更はユーザー判断を記録し、後続の計画と受入条件を更新する。
